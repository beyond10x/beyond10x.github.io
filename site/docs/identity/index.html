identity/README.md · 0c8574131c24

The platform's login and principal service. It owns upstream OpenID Connect login, tenant-scoped principal identity, opaque CLI sessions, the server-side credential store, the organization directory, and the personal collaboration profile.

Without it, every product service runs its own upstream OAuth, keeps its own copy of who works here and defines what a user identifier means. Upstream provider tokens never leave this process, and upstream provider credentials never reach a consumer. A user key is always (tenant, sub) and never a bare subject. Every consumer resolves an authority bound to one exact registered audience.

Where it sits​

Identity consumes a generically configured upstream OIDC provider and either SQLite or PostgreSQL. Relying parties resolve sessions or five-minute opaque access credentials through exact, opaque audience registrations. Identity contains no relying-party endpoint, provider integration, product name, or capability vocabulary.

A consumer's registration decides what it holds:

consumerholdsresolves it at
an in-cluster application registered as a session audiencethe person's Identity session, presented with the exact audience in the x-b10x-audience headerGET /v1/session-authority
a caller of the directory or profile routesthe person's Identity session, presented with the route's fixed audience/v1/directory/…, /v1/profile/…
a relying party registered as an access audiencea five-minute access credential for that one audience and scope set, never the session; an authenticated session mints it through POST /v1/access-token, and a public PKCE client receives it from /oauth/authorize with the exact resourceGET /v1/access-authority

Resolving a session returns the person's authority for that audience. It never mints a reusable token and never reaches another subject. A consumer's scope is a coarse gate only, so the consumer must still run its own admission before an effect-bearing operation.

Status​

Identity is the deployable human-login and relying-party authority slice. The source is public. The crates are deployment components and are not published to crates.io.

The former-brand fence is not a step here: it runs organization-wide as Atlas's scripts/check-org-brand.sh.

The crate needs Rust 1.89 or newer, uses edition 2024 and sets unsafe_code = "forbid". The gate and the image build use the rustc pinned in rust-toolchain.toml.

The PostgreSQL arm runs against a real server and reports itself skipped when IDENTITY_TEST_POSTGRES_URL is unset:

IDENTITY_TEST_POSTGRES_URL='postgresql://user:password@host:5432/identity?sslmode=disable' \
  cargo test --locked the_postgres_arm

check-audit.sh carries one transitive exception: openidconnect 4.1.0 pulls rsa 0.9 unconditionally. This service uses that crate only to verify signatures with public JWKs and never holds an RSA private key. The script first proves the dependency path is still exactly identity -> openidconnect -> rsa, and any drift forces re-review. The exception goes when the upstream dependency stops carrying that crate.

Running it locally​

Create an upstream OIDC web client whose authorized redirect URI is exactly http://127.0.0.1:8080/oauth/callback/upstream, then:

IDENTITY_LISTEN=127.0.0.1:8080 \
IDENTITY_PUBLIC_ORIGIN=http://127.0.0.1:8080 \
IDENTITY_TENANT_ID=local \
IDENTITY_UPSTREAM_ISSUER=https://accounts.example.com \
IDENTITY_UPSTREAM_CLIENT_ID='your-client-id' \
IDENTITY_UPSTREAM_CLIENT_SECRET='your-client-secret' \
IDENTITY_UPSTREAM_ORGANIZATION_DOMAIN_CLAIM=organization \
IDENTITY_ORGANIZATION_TENANTS_JSON='[{"claimValue":"example.com","tenantId":"local"}]' \
IDENTITY_AUDIENCE_REGISTRY_JSON='{"version":"identity.audiences/2","session":["urn:example:console"],"access":[{"audience":"urn:example:resource-api","scopes":["resource.read"],"groupScopes":[{"group":"operator","scopes":["resource.write"]}]}]}' \
IDENTITY_DATABASE_PATH=/tmp/identity/private/identity.sqlite3 \
cargo run --locked

IDENTITY_UPSTREAM_CA_BUNDLE optionally names a PEM bundle of additional trusted roots for upstream OIDC HTTPS requests, such as a private certificate authority or a disposable local deployment. Certificate and hostname verification stay on. The file must contain certificates and be no larger than 1 MiB. An unreadable or invalid configured bundle refuses startup. Without the variable the built-in roots apply. The bundle covers every configured upstream provider and does not enable the development login route.

The three IDENTITY_UPSTREAM_* variables remain the single-provider compatibility surface. A deployment with several providers instead supplies a credential-free registry whose clientSecretEnv entries name separately injected environment variables:

IDENTITY_UPSTREAM_PROVIDERS_JSON='[{"id":"one","label":"Provider one","issuer":"https://accounts.example.com","clientId":"client-one","clientSecretEnv":"IDENTITY_PROVIDER_ONE_SECRET","organizationDomainClaim":"organization","organizationTenants":[{"claimValue":"example.com","tenantId":"local"}]}]'

The authorization request selects a provider through its identity_provider parameter. When more than one provider is configured, a browser request that omits the selection receives an Identity-owned chooser that preserves the exact authorization request. An explicit unknown selection is refused. Login state binds the provider id, so a callback code can be exchanged only against the issuer and client that started it.

Additional identities are linked only from a live Identity session through /v1/identity-links. Email equality never links people, and the final login method cannot be removed.

A deployment may admit a confidential service to exchange one exact access authority for another. The exchange is disabled by default. A caller declaration holds only the name of an environment variable, and the secret is injected separately from deployment-owned secret material:

IDENTITY_TRUSTED_ACCESS_CALLERS_JSON='[{"id":"relying-service","secretEnv":"IDENTITY_RELYING_SERVICE_EXCHANGE_SECRET"}]'
IDENTITY_ACCESS_EXCHANGE_POLICIES_JSON='[{"callerId":"relying-service","sourceAudience":"urn:example:published-resource","requiredSourceScopes":["published.call"],"targetAudience":"urn:example:resource-api","allowedTargetScopes":["resource.read"]}]'

POST /v1/access-exchange requires the source access token in Authorization and the confidential caller in x-b10x-access-exchange-caller plus x-b10x-access-exchange-secret. Identity binds the request to the exact policy, requires a human self-actor, recomputes current groups, re-applies the target audience policy, and returns the ordinary five-minute verifier-only target credential. The calling service must never forward that credential to the public client whose source token it exchanged.

Production configuration refuses a non-HTTPS public origin. Plain HTTP is accepted only for the literal 127.0.0.1 local-test origin.

Signing in on a workstation​

A workstation has no upstream provider to redirect to, so the flow above cannot complete there. The optional local-login feature replaces only the step that has no counterpart: /oauth/authorize asks which mailbox to sign in as and mints the ordinary authorization code. Everything after that is unchanged.

A feature build needs no upstream provider: leave out every IDENTITY_UPSTREAM_* variable and it starts with the local sign-in only. A partly configured provider is still refused, and a default build still requires IDENTITY_UPSTREAM_ISSUER.

IDENTITY_LISTEN=127.0.0.1:8080 \
IDENTITY_PUBLIC_ORIGIN=http://127.0.0.1:8080 \
IDENTITY_TENANT_ID=local \
IDENTITY_AUDIENCE_REGISTRY_JSON='{"version":"identity.audiences/2","session":["urn:example:console"],"access":[{"audience":"urn:example:resource-api","scopes":["resource.read"]}]}' \
IDENTITY_DATABASE_PATH="$PWD/target/identity-local/identity.sqlite3" \
cargo run --locked --features local-login

With a provider configured as well, it is discovered before the listener opens, as in a default build. The provider then serves only identity links, because /oauth/authorize signs in locally.

Issuing a session for a mailbox somebody typed authenticates nobody. Three independent rules refuse it in a deployment, and any one of them is sufficient:

Deploying​

Dockerfile builds the image: distroless, the nonroot user, port 8080, volume /var/lib/identity. Startup validates the whole environment below, fetches every upstream provider's OIDC discovery document, opens the store, and only then binds the listener. Any failure exits non-zero.

Constraints (AGENTS.md invariant 7 and the safety envelope):

constraintrule
one replica, replacement rolloutsApplies on either backend. Capacity check-and-insert admission is serialized inside one process. A second process, including the overlap of a rolling update, is not proven safe.
SQLite directoryA non-symlink directory owned by the process user with no group or other permission bit (0700 or stricter). Identity creates it at 0700 when it is missing. A volume that grants group access is refused.
SQLite fileAn existing database must be a non-symlink regular file owned by the same user with no permission beyond 0600. Identity sets it to 0600 on every start.
configuration changes end sessionsThe issuer, tenant, CLI client, providers with their organization policy, web clients, audience registry and access-exchange policies form the session configuration generation. Changing any of them requires every person to log in again. Group assignments and secrets are not part of it.

Audiences​

Every authority-bearing call names exactly one audience, verbatim. The vocabulary is wire-visible: it is minted into issued tokens and required by every relying party, so it moves only as a protocol change with a migration. The required, versioned IDENTITY_AUDIENCE_REGISTRY_JSON admits extensible relying parties. Adding an audience is deployment configuration after the relying parties have released the same exact byte.

Registered access and session audiences are reached as the table in Where it sits shows. The fixed audiences are:

audiencereached by
urn:b10x:directoryevery /v1/directory/… route, in x-b10x-audience
urn:b10x:profilethe person's own control surface
urn:b10x:profile-projectionthe learning consumer: it reaches the projection and the learning write, and nothing else. The durable store, the withheld statements and the lifecycle controls are not addressable under it

More columns: swipe horizontally, or focus the table and use the arrow keys.

The registry document is closed and deterministic:

{
  "version": "identity.audiences/2",
  "session": ["urn:example:console"],
  "access": [{
    "audience": "urn:example:resource-api",
    "scopes": ["resource.read"],
    "groupScopes": [{"group": "operator", "scopes": ["resource.write"]}]
  }]
}

Audience and scope bytes are opaque registration data. scopes are available to every authenticated subject. An exact groupScopes entry can expand issuance for subjects carrying that verified group. Identity only enforces the closed registration. The relying party owns the meaning of those bytes and every operation-level authorization decision.

Unknown versions and fields, duplicate identifiers or rules, malformed names, unregistered audiences and unregistered scopes are refused. The canonical registry is part of the session configuration generation, so changing it requires a new login.

The standard authorization-server document advertises no dynamic client registration. A deployment registers one public client ID. Its loopback callback accepts an ephemeral port, and PKCE S256 is mandatory. An OAuth resource authorization never creates a reusable browser session: the one-use code is bound to its exact registered audience and scope and exchanges directly for the same five-minute access-token authority used by /v1/access-token.

The person may see exactly what a consumer is given. A consumer may see nothing else.

Request bodies are capped at 64 KiB. Upstream OIDC uses a five-second connect and fifteen-second total deadline. Session, access-token and authority responses carry no-store and no-cache.

Session credentials use the opaque identity_session_v1_ format and short-lived access credentials use identity_access_v1_. Callers must treat both as indivisible bearer values. The resolved authority vocabulary is product-neutral: tenant_id and principal_kind carry the tenant and actor kind without an inherited product namespace.

The credential tables, the directory and the profile have finite row caps. Listings are capped and are not paginated.

The rules that shape the code​

The full statements are in AGENTS.md.

Tenant is resolved from a cryptographically verified upstream claim, before any code or session exists. A provider resolves it in one of three modes:

  1. Exact mapping (IDENTITY_ORGANIZATION_TENANTS_JSON, or a provider's organizationTenants): the claim value maps to its tenantId. Suffix matching, email domains, request hints and IDENTITY_TENANT_ID are never fallbacks.
  2. No organization claim configured: every login of that provider gets IDENTITY_TENANT_ID.
  3. Legacy base-domain allowlist (IDENTITY_ALLOWED_ORGANIZATION_BASE_DOMAINS, mutually exclusive with the mapping): a claim equal to a listed domain or ending in . plus it gets IDENTITY_TENANT_ID.

Modes 2 and 3 are single-tenant compatibility modes. Unknown, duplicate, non-string and unmapped claims fail closed. See the tenant-resolution decision.

rulestatement
nothing reusable is stored in the clearAuthorization codes, sessions and access tokens are stored only as SHA-256 verifiers. Provider access and refresh tokens are never persisted.
sessions are bound to issuer, tenant and configuration generationChanging the authority-defining configuration requires a new login.
a directory group carries no authorityOnly the deployment-configured static group assignments reach an authority response. Adding a principal to a directory group grants nothing. Directory writes require the static group identity-directory-admin, so administration is deployment configuration and can never be granted from inside the directory.
groups are flat and membership is directOne bounded indexed query, with no recursion and no transitive closure. Hierarchy belongs to the collaboration product.
an inference does not become a confirmation by itselfThe profile learning path admits only observed and inferred. The only transition into confirmed is an explicit act by the person.
secret material never enters a profile projectionContent and source references are screened for credential markers, vendor prefixes, JWT shape, URL user info and long opaque tokens, on write and again when a snapshot is built. A row that arrived by another route therefore still cannot reach a model.
schema changes are additive onlyEvery statement is CREATE … IF NOT EXISTS. An older binary keeps working against a newer schema.
